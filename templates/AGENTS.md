# 项目开发约定

项目目标、运行方式和当前限制见 README.md。以本轮用户要求确定改动范围。

- 修改前查找现有实现及调用方；复用已有规则，完成受影响的调用、测试、配置和文档。
- 优先少量职责完整的模块和小接口，让实现吸收复杂度。合并只转发、改名或重复检查的薄层；保留确实隐藏算法、存储或外部系统差异的边界。
- 一次性逻辑直接写在使用处；当提取能隔离独立概念、减少重复维护或明显改善理解时，再提取函数。新增依赖和配置项要解决当前需要。
- 修复缺陷时检查同一路径的其他调用；删除旧实现前核查代码、脚本、配置和文档中的引用。
- 在数据进入可信内部表示的边界完成校验，内部直接使用。仅在数据被修改、跨信任边界或有未保证的不变量时再次检查。删除重复类型转换、重复校验和无实际用途的防御分支，保留必要的数据保护和错误处理。
- 使用 README 中已经验证的命令；按改动影响运行检查。新增非简单逻辑或修复缺陷，应验证实际行为及有关边界；格式和错别字修改无需新增测试。
- 核验和审查应回答具体问题；已有结果足够且代码未再变化时结束检查。合并重复检查，删除只验证已废弃实现的测试和无人使用的报告；保留仍能发现独立故障的检查。
- 当前行为在现有文档中就地更新；历史由 Git 或实验记录保存。一次性任务过程留在会话，需跨会话接续时只维护一份当前计划。
- 精简同样适用于文档、脚本、配置和流程：删除无当前用途的预案、重复免责声明、转发脚本、重复说明和检查包装层；把必要内容并回使用处。保留会影响行动或结论的限制及不可重建证据。
- 规则只记录项目中稳定、必要且不易从代码发现的约束。新增规则时检查已有条目能否修改；个案错误先修复，确有跨任务适用性才推广。
- 说明谁对什么做了什么，产生什么可观察结果。使用领域内已有名称，首次出现的不熟悉术语给一句解释；避免用抽象名词代替具体行为。
- 改写保留对象与数值的对应、单位、否定、条件、比较范围、因果关系、引用及不确定性。词表命中只提示检查，按语境决定修改。
- 常规、可逆且属于当前任务的工作直接完成；破坏性操作或新增外部影响超出授权时，先说明具体对象和后果。
- 交付说明完成的行为、验证结果和仍影响使用的限制。新增依赖、保留兼容层或额外入口时说明必要性；无需每轮另建报告文件。

采用项目已配置的增长预算；超限时精简无用途内容或申请有理由的增长，不自行放宽上限、排除统计对象或冒充批准。正常文件放入其职责目录，保留一个现役实现入口；清理验证后收紧预算，历史证据保持可追溯。
